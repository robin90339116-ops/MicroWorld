# 迭代复盘｜从“流程能展示”到“结果可解释”

[返回展示首页](README.md) · [逐项证据](evidence.md)

这是基于已有提交与验收记录的回顾，不补造当时不存在的用户研究或团队会议。

## 1. 原型与实现之间的落差

历史规格包含熟人免确认、门贴、支付、地图与数字藏品等完整愿景，但页面存在不意味着外部能力可用。展示材料重新区分设计、代码、自动验收、真机和上线五种状态。

**产品启示：**验收标准必须描述业务事实，而不是“有成功页”。支付是否被真实核验、奖励是否能恢复、双方是否真正同意，都应独立验收。

## 2. 取消与结果未知，不能用同一句“失败”概括

会话可能等待对方、已完成但响应丢失、已取消或过期。用户看到网络错误时，不应被迫猜测是否需要重做。

**实际调整：**安全检查点绑定账号和后端；恢复先查原会话；完成后读原奖励快照；取消以服务端结果为准。

**代价：**增加状态复杂度和文案要求。仍需真机检验这些提示是否让普通用户理解，不能仅因服务端测试通过就结束设计。

## 3. 不完整但诚实，比模拟完整更能推进交付

真实支付缺失时，服务端关闭支付和商品评价资格；默认纪念凭证不上链；商家凭证不再标作已完成硬件/GPS 认证。

**产品启示：**路线图与演示可以呈现愿景，但必须防止未开通能力影响真实用户决策。对招聘展示也应采用相同标准。

## 4. 真实环境比“更多测试数字”更有价值

实库回归发现 JSONB 字段顺序不能按字符串比较；TLS 实测发现 IP 证书身份校验缺口；容器重启暴露动态端口变化；干净构建发现镜像依赖未提交的数据文件。这些问题不是新增一个成功按钮能解决的。

**产品启示：**分阶段测试要覆盖用户真实依赖的环境边界。发布门槛可以用工程证据支持，但不要把测试数量写成用户价值指标。

## 5. 当前最需要纠正的投入方向

账号、存储与部署准备已有较充分的自动验收；目标用户是否愿意改变既有联系习惯，仍缺少真实证据。继续扩展地图、链和奖励之前，应先完成核心场景的用户验证与双机演示。

## 下一阶段路线图（建议，不是交付承诺）

| 优先级 | 工作 | 进入条件 | 完成标准 |
|---|---|---|---|
| P0 | 核心流程原型测试 | 目标参与者同意参加 | 有真实观察、反例和明确修改决策 |
| P0 | 个人双机与页面验收 | 两部可调试手机、同一测试后端 | 首次/取消/超时/重试/恢复可完整演示，问题留档 |
| P1 | 真地图、定位与测试环境 | 平台配置及可用测试资源 | 真机出图和错误路径验收，不使用演示位置冒充真实 |
| P1 | 商家到店试验 | 商家登记和可测试设备 | 到店评价规则可解释，重复操作不重复发奖 |
| P2 | 真实支付与真实上链 | 对应资源、资质及明确用户价值 | 回调/查单/退款或链上回执等完整验收 |
| 暂缓 | AR、智能导游、复杂世界扩展 | 核心价值得到支持 | 另立范围和验证标准，不挤占核心链路 |

不提前给未知资源依赖设定虚构上线日期；不因希望展示更多功能而跳过前序门槛。
