# 产品案例｜一次相遇之后，关系如何继续？

[返回展示首页](README.md)

## 1. 项目背景：这是一个待验证的问题，而非既定结论

MicroWorld 的起点不是「做一个带 NFC 和 NFT 的 App」，而是一个场景假设：人们可能在线下活动中有过愉快交流，却缺少保留相遇来源、表达双向意愿和继续互动的顺畅方式。

直接交换联系方式已经是低成本替代方案。因此本产品真正需要回答的是：**用户为什么愿意多完成一次碰触与确认，而不是直接加好友？** 如果答案只是获得积分，未必足以支撑长期使用。

目前没有提供可核验的用户访谈或市场调研原始记录。以下用户需求与商业机会均是待验证假设，不能包装成研究结论。

## 2. 缩小目标场景

| 场景 | 可能的需求 | 暂不承诺 |
|---|---|---|
| 兴趣活动中认识新朋友 | 互相确认、记住在哪里认识、方便继续交流 | 陌生人匹配效率优于现有社交工具 |
| 熟人再次相遇 | 留下共同经历，不反复创建关系 | 纪念徽章一定提高留存 |
| 商家到店 | 将评价资格与一次到店交互关联 | 已杜绝刷评或证明真实消费 |

面向下一轮验证，优先聚焦「兴趣活动后的双方连接」。商家场景保留为独立业务分支，不把支付、商家运营和陌生人匹配同时当作首发必需项。

## 3. 定义最小价值闭环

个人链路：发起碰一碰 → 交换会话信息 → 两人明确确认 → 建立双方可见的连接 → 继续聊天、查询本次记录。

商家链路：登记商家终端 → 交换动态会话 → 消费者打卡 → 评价地点 → 返回评价及奖励结果。支付核验尚未接入，因此不开放商品评价。

两条链路共用的是「交互必须有来源，状态必须可恢复」的原则，而不是共用一套确认界面。个人强调同意和关系；商家强调登记、凭证与评价资格。

## 4. 关键决策：把风险转化为产品规则

### 决策一：NFC 是入口，不是绝对真实性保证

二维码、直接加好友和蓝牙都是需要比较的替代方案。选择 NFC 的产品意图是让用户明确感知「这次交互发生在靠近的动作中」。代价是设备兼容、双端准备和识别失败，且仍无法单凭 NFC 排除中继、串通或改造客户端。

因此展示文案使用「线下交互记录」「双方确认的连接」，不用「不可伪造凭证」。是否保留这一入口，最终要由任务完成率、耗时和用户复用意愿决定。

### 决策二：熟人也暂不免确认

历史原型曾设计熟人复次碰面自动发放纪念奖励。当前实现保留双方确认：优先统一同意与结果归属，减少误触和恢复时的歧义。好处是边界清楚，代价是熟人场景多一步操作。

后续只有在真机与用户测试中证明重复确认造成明显负担，且能设计明确的授权与撤回机制后，才重新评估快捷模式。

### 决策三：不把「客户端说支付成功」当成消费证明

商家地点与商品的评价资格不同。当前缺少真实支付服务，所以服务端拒绝未核验的支付状态，不让旧模拟订单解锁商品评价。这里主动牺牲了演示上的“完整感”，换取业务状态的可信表达。

## 5. 推进方式：按闭环风险排优先级

实际交付先修正常使用问题，再补个人与商家会话、确认及恢复，随后补数据库和部署可靠性。版本提交与测试记录可追溯，但自动测试不能替代真机验收。

接下来的建议顺序是：

1. 核心流程原型可理解性测试；确认用户理解双方确认和结果状态。
2. 两部鸿蒙真机完成个人碰一碰，记录成功、超时、取消与重试。
3. 真实定位、地图和测试环境部署，形成可连续演示的版本。
4. 商家小范围验证；有渠道与资质后再安排支付。
5. 根据用户对纪念价值的反馈，决定是否投入真实上链。

这是下一阶段的优先级建议，不是已经发生的用户验证或商业试点。

## 6. 当前成果：交付证据，而不是虚构经营指标

- 已实现个人双向确认、账号范围内的关系和聊天、商家登记终端与评价资格相关逻辑，保留失败和恢复路径。
- 自动验收覆盖重复请求、状态恢复、数据库事务、TLS、崩溃恢复、备份与容器替换；最新已核验后端测试为 79 项。
- 真实支付、华为云上线、真实 NFT 铸造及完整双机体验仍未验收。
- 没有宣称获客、留存、收入、转化率提升或用户满意度成果。

证据和状态逐项列在 [evidence.md](evidence.md)，工程证据不作为用户价值的替代品。

## 7. 复盘：下一步应验证什么

工程侧已对「重复请求不会重复执行」「恢复时不虚构成功」投入较多，但对「用户为什么需要它」仍缺少真实证据。下一阶段最重要的工作不是增加更多功能，而是让目标用户完成一次核心任务，并看见他们在哪里不理解、不愿意或无法继续。

如果多数目标用户认为直接加好友更自然，应该重新界定场景或收缩产品，而不是用更多奖励掩盖价值不足。
